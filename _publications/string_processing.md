## Unicode string-երի մշակումը Elixir-ում

[Unicode-ի ստեղծման պատմությունը](./unicode_and_utf.md) հոդվածում տեսանք, թե Unicode-ն ինչպես է թվային արժեքներ հատկացնում նշաններին, իսկ UTF-8-ը՝ ինչպես է այդ արժեքները ներկայացնում բայթերով։ Գիտենք նաև, որ Elixir-ի string-ը UTF-8-ով կոդավորված binary տվյալների տիպ է։

Սակայն տեքստի հետ աշխատելիս միայն բայթերի քանակը կամ code point-երը հաշվելը բավարար չէ։ Մեկ տեսանելի նշանը կարող է կազմված լինել մի քանի code point-ից։ Արտաքինից նույն տեսքն ունեցող երկու string կարող են տարբեր բայթեր պարունակել։ Արտաքին աղբյուրից ստացված binary-ն էլ կարող է ընդհանրապես վավեր UTF-8 չլինել։

Այս հոդվածում կդիտարկենք, թե Elixir-ն ինչպես է լուծում այդ խնդիրները։ Կծանոթանանք grapheme-ներին (մասնագիտական գրականության մեջ տերմինը երբեմն հայերեն թարգմանվում է որպես գրույթ), Unicode նորմալացմանը և `String` module-ի այն գործիքներին, որոնք անհրաժեշտ են տեքստերը ճիշտ ու անվտանգ մշակելու համար։

### Բայթ, code point և grapheme

Unicode string-ի չափը կարելի է դիտարկել երեք տարբեր մակարդակով։

**Բայթը** ցույց է տալիս, թե տվյալը որքան տարածք է զբաղեցնում UTF-8 ներկայացման մեջ։ `byte_size/1` ֆունկցիան հաշվում է հենց բայթերը։

**Code point-ը** Unicode-ի կողմից նշանին տրված թվային արժեքն է։ UTF-8-ում մեկ code point-ը կարող է զբաղեցնել մեկից չորս բայթ։

**Grapheme-ը** մեկ տեսանելի նշանին մոտ հասկացություն է։ Այն կարող է կազմված լինել մեկ կամ մի քանի code point-ից։ Elixir-ի `String` module-ը string-ի երկարությունը և դիրքերը հիմնականում հաշվում է grapheme-ներով։

Դիտարկենք երեք պարզ օրինակ։

```elixir
iex> byte_size("A")
1
iex> length(String.codepoints("A"))
1
iex> String.length("A")
1

iex> byte_size("Ա")
2
iex> length(String.codepoints("Ա"))
1
iex> String.length("Ա")
1
```

`A`-ն մեկ բայթ, մեկ code point և մեկ grapheme է։ `Ա`-ն երկու բայթ է, բայց շարունակում է մնալ մեկ code point և մեկ grapheme։

Հիմա ստեղծենք `é` տեսքն ունեցող string՝ առանձին `e` տառից և դրա վրա դրվող շեշտի նշանից։ `\u0065`-ը `e` տառն է, իսկ `\u0301`-ը՝ նախորդ նշանին միացող շեշտը։ Այդպիսի նշանը կոչվում է **combining mark**՝ համակցվող նշան։

```elixir
iex> text = "\u0065\u0301"
"é"
iex> byte_size(text)
3
iex> length(String.codepoints(text))
2
iex> String.length(text)
1
```

Այս string-ը երեք բայթ է և երկու code point, բայց ընթերցողի համար մեկ տեսանելի նշան է։ Այդ պատճառով այն մեկ grapheme է։

Grapheme-ը միշտ չէ, որ ճշգրիտ համընկնում է որևէ լեզվի այբուբենում ընդունված «մեկ տառ» հասկացության հետ։ Elixir-ը կիրառում է Unicode-ի Extended Grapheme Cluster կանոնները և հաշվի չի առնում յուրաքանչյուր լեզվի բոլոր առանձնահատկությունները։ Այնուամենայնիվ, օգտագործողի տեսանկյունից string-ի երկարությունը և դրա հատվածները որոշելու համար grapheme-ը սովորաբար ամենահարմար միավորն է։

### `String.codepoints/1` և `String.graphemes/1`

`String.codepoints/1` ֆունկցիան string-ը բաժանում է առանձին code point-երի։ Յուրաքանչյուր տարր վերադարձվում է որպես UTF-8 string, ոչ թե ամբողջ թիվ։

```elixir
iex> String.codepoints("Բարև")
["Բ", "ա", "ր", "և"]

iex> String.codepoints("\u0065\u0301")
["e", "́"]
```

Երկրորդ օրինակում շեշտը ցուցադրվում է որպես առանձին code point։ 

`String.graphemes/1` ֆունկցիան նույն string-ը բաժանում է grapheme-ների։

```elixir
iex> String.graphemes("Բարև")
["Բ", "ա", "ր", "և"]

iex> String.graphemes("\u0065\u0301")
["é"]
```

Առաջին օրինակում code point-երի և grapheme-ների ցուցակները համընկնում են։ Երկրորդում երկու code point-երը միավորվում են մեկ grapheme-ի մեջ։

Այս տարբերությունը կարևոր է, օրինակ, օգտատիրոջ անվան առավելագույն երկարությունը ստուգելիս։ Բայթերի կամ code point-երի քանակը սահմանափակելը կարող է օգտագործողի համար անսպասելի արդյունք տալ։ Եթե պահանջը վերաբերում է տեսանելի նշանների քանակին, պետք է օգտագործել `String.length/1`։ Եթե սահմանափակումը վերաբերում է տվյալների պահպանման չափին, պետք է ստուգել `byte_size/1`-ը։ Սրանք երկու տարբեր պահանջներ են։

### Ինչո՞ւ է `String.length/1`-ը հաշվում grapheme-ները

Elixir-ի `String.length/1` ֆունկցիան վերադարձնում է ոչ թե բայթերի կամ code point-երի, այլ grapheme-ների քանակը։

```elixir
iex> composed = "\u00E9"
"é"
iex> decomposed = "\u0065\u0301"
"é"

iex> String.length(composed)
1
iex> String.length(decomposed)
1
```

Երկու string-երն էլ ընթերցողի համար մեկ նշան են, ուստի երկուսի երկարությունն էլ `1` է։ Սակայն դրանց ներքին կառուցվածքը տարբեր է։

```elixir
iex> byte_size(composed)
2
iex> byte_size(decomposed)
3

iex> String.codepoints(composed)
["é"]
iex> String.codepoints(decomposed)
["e", "́"]
```

### Արտաքինից նույնը, բայց ներսից տարբեր կառուցվածքով string-եր

Նախորդիվ ցուցադրված `é` տառի երկու օրինակները էկրանին սովորաբար նույն տեսքն ունեն։ Առաջինը մեկ code point է՝ `U+00E9 LATIN SMALL LETTER E WITH ACUTE`։ Երկրորդը կազմված է `U+0065 LATIN SMALL LETTER E` և `U+0301 COMBINING ACUTE ACCENT` code point-երից։

```elixir
iex> composed = "\u00E9"
"é"
iex> decomposed = "\u0065\u0301"
"é"

iex> composed == decomposed
false
```

`==` օպերատորը համեմատում է string-երի բայթերը։ Քանի որ երկու ներկայացումների բայթերը տարբեր են, արդյունքը `false` է։ Տառատեսակը կարող է դրանք նույն կերպ ցուցադրել, բայց դա դրանց հավասար չի դարձնում։

Այսպիսի տարբեր ներկայացումներ կարող են հայտնվել տարբեր ստեղնաշարերից, օպերացիոն համակարգերից, պատճենված տեքստից կամ արտաքին ֆայլերից։ Եթե ծրագիրը դրանք համեմատում է առանց նախնական մշակման, որոնումը, եզակիության ստուգումը կամ տվյալների խմբավորումը կարող են սխալ արդյունք տալ։ Այդ խնդիրը լուծում է Unicode նորմալացումը։

### Ի՞նչ է Unicode նորմալացումը

Unicode նորմալացումը նույն իմաստն ունեցող string-ի ներկայացումները բերում է նախապես սահմանված ընդհանուր ձևի։ Այն չի փոխում string-ի կոդավորումը․ արդյունքը Elixir-ում շարունակում է մնալ UTF-8 binary։ Փոխվում է string-ում օգտագործվող code point-երի հաջորդականությունը։

Unicode-ը տարբերում է երկու տեսակի համարժեքություն։

**Canonical equivalence-ը** վերաբերում է ներկայացումներին, որոնք պետք է նույն նշանն արտահայտեն և ճիշտ ցուցադրվելիս նույն տեսքն ու վարքն ունենան։ Մեկ `é` code point-ը և `e` ու combining acute accent հաջորդականությունը canonical equivalent են։

**Compatibility equivalence-ը** ավելի լայն հասկացություն է։ Այն կարող է հավասարեցնել նաև այնպիսի ներկայացումներ, որոնց արտաքին տեսքը կամ հատուկ նշանակությունը տարբերվում է։ Օրինակ՝ շրջանագծված `①` նշանը `Compatibility equivalence` նորմալացումից հետո կարող է դառնալ սովորական `1` թվանշան։

Unicode-ը սահմանում է նորմալացման չորս ձև։

| Ձև | Հիմքը | Արդյունքի կառուցվածքը |
|---|---|---|
| NFC | Canonical equivalence | Հնարավորության դեպքում միավորված code point-եր |
| NFD | Canonical equivalence | Բաղադրիչների բաժանված code point-եր |
| NFKC | Compatibility equivalence | Բաժանում, ապա հնարավոր միավորում |
| NFKD | Compatibility equivalence | Բաղադրիչների բաժանում |

Անվան վերջին տառն օգնում է հիշել տարբերությունը։ `C`-ն նշանակում է *composition*՝ միավորում, իսկ `D`-ն՝ *decomposition*՝ բաժանում։ `K`-ն ցույց է տալիս, որ կիրառվում են նաև compatibility կանոնները։

### NFC և NFD

NFD-ն canonical equivalent նշանները բաժանում է բաղադրիչների։ NFC-ն նախ կատարում է նույն բաժանումը, ապա հնարավոր բաղադրիչները նորից միավորում է մեկ code point-ի մեջ։

```elixir
iex> String.normalize("\u00E9", :nfd)
"é"

iex> String.normalize("\u0065\u0301", :nfc)
"é"
```

NFC-ն սովորաբար հարմար ընտրություն է սովորական տեքստը պահպանելու և համեմատելու համար, բայց ծրագիրը պետք է ունենա հստակ կանոն և նույն կանոնը կիրառի տվյալների մուտքի բոլոր ուղիներում։ Միայն ենթադրել, որ մուտքային տեքստն արդեն NFC է, անվտանգ չէ։

NFD-ն օգտակար է այնպիսի մշակման ժամանակ, երբ անհրաժեշտ է առանձին աշխատել հիմնական տառի և դրան միացող նշանների հետ։ Օրինակ՝ որոշ որոնման համակարգեր կարող են այդ ձևով մշակել շեշտերը։ Սակայն շեշտը պարզապես հեռացնելը լեզվական առումով միշտ չէ, որ ճիշտ է, ուստի նման որոշումը պետք է բխի ծրագրի պահանջներից։

### NFKC և NFKD

NFKC-ն ու NFKD-ն կիրառում են ոչ միայն canonical, այլև compatibility համապատասխանությունները։ Դրանք կարող են հեռացնել արտաքին ձևի որոշ տարբերություններ։

```elixir
iex> String.normalize("①", :nfkc)
"1"

iex> String.normalize("ﬁ", :nfkd)
"fi"
```

Այս ձևերը կարող են օգտակար լինել, երբ ծրագրի կանոններով `①`-ը և `1`-ը պետք է նույն արժեքը նշանակեն։ Բայց դրանք չի կարելի առանց մտածելու կիրառել ցանկացած տեքստի նկատմամբ։ `compatibility equivalence` նորմալացումը կարող է ջնջել այն տարբերությունը, որը տվյալ ծրագրի համար կարևոր է։ Օրինակ՝ մաթեմատիկական ֆորմուլների կամ բնագրի ճշգրիտ տեսքի պահպանման ժամանակ արտաքին ձևը կարող է իմաստ ունենալ։

Նորմալացումը նաև չի փոխարինում փոքրատառ ու մեծատառ տարբերակների մշակմանը, բացատների մաքրմանը կամ տառադարձությանը։ Դրանք առանձին գործողություններ են և պետք է սահմանվեն ծրագրի կանոններով։

### `String.normalize/2`

Elixir-ի `String.normalize/2` ֆունկցիան ընդունում է string-ը և նորմալացման ձևը։ Հնարավոր ձևերն են `:nfc`, `:nfd`, `:nfkc` և `:nfkd`։

```elixir
iex> text = "\u0065\u0301"
"é"

iex> normalized = String.normalize(text, :nfc)
"é"

iex> normalized == "\u00E9"
true
```

Եթե նույն արժեքը հաճախ է համեմատվելու կամ որոնվելու, ավելի արդյունավետ է այն մեկ անգամ նորմալացնել մուտքի ժամանակ և պահպանել այդ ձևով։ Յուրաքանչյուր համեմատությունից առաջ նույն string-ը կրկին նորմալացնելը ավելորդ աշխատանք է։

Կարևոր է նաև գործողությունների հերթականությունը։ `String.normalize/2`-ը անվավեր UTF-8 code point-երը բաց է թողնում և շարունակում է մշակել մնացած string-ը։ Եթե տվյալների լուռ կորուստը ցանկալի չէ, binary-ն պետք է նախ ստուգել `String.valid?/1`-ով և միայն դրանից հետո նորմալացնել։

### `String.equivalent?/2`

`String.equivalent?/2` ֆունկցիան ստուգում է երկու string-երի canonical equivalence-ը։ Այն երկու արժեքները NFD ձևի է բերում և հետո համեմատում։

```elixir
iex> String.equivalent?("\u00E9", "\u0065\u0301")
true

iex> String.equivalent?("Elixir", "elixir")
false
```

Այս ֆունկցիան հաշվի է առնում canonical տարբեր ներկայացումները, բայց չի անտեսում մեծատառ ու փոքրատառ տարբերությունը և չի կիրառում `compatibility equivalence` նորմալացում: Հետևաբար այն ընդհանուր նշանակության «մոտավորապես հավասար» համեմատություն չէ։

Եթե երկու string պետք է compatibility կանոններով համեմատել, ընտրված ձևը պետք է բացահայտ կիրառել երկուսի նկատմամբ։

```elixir
iex> String.normalize("①", :nfkc) == String.normalize("1", :nfkc)
true
```

### Հայերեն `և`-ի նորմալացման առանձնահատկությունը

Հայերեն `և` նշանը Unicode-ում ունի առանձին `U+0587 ARMENIAN SMALL LIGATURE ECH YIWN` code point-ը։ Unicode-ը դրա համար սահմանում է compatibility decomposition՝ `U+0565` (`ե`) և `U+0582` (`ւ`)։

Սա նշանակում է, որ NFC-ն և NFD-ն `և`-ը չեն բաժանում, իսկ NFKC-ն ու NFKD-ն այն վերածում են երկու code point-ից կազմված `եւ` հաջորդականության։

```elixir
iex> String.normalize("և", :nfc)
"և"

iex> String.normalize("և", :nfd)
"և"

iex> String.normalize("և", :nfkc)
"եւ"

iex> String.normalize("և", :nfkd)
"եւ"
```

Այս փոխակերպումը ազդում է նաև string-ի կառուցվածքի և երկարության վրա։

```elixir
iex> String.codepoints("և")
["և"]

iex> String.codepoints("եւ")
["ե", "ւ"]

iex> String.length("և")String.normalize("և", :nfd)
1

iex> String.length("եւ")
2
```

`String.equivalent?/2`-ը canonical համարժեքություն է ստուգում, ուստի այս երկու տարբերակները համարժեք չի համարում։

```elixir
iex> String.equivalent?("և", "եւ")
false
```

NFKC կիրառելուց հետո դրանք դառնում են հավասար։

```elixir
iex> String.normalize("և", :nfkc) == String.normalize("եւ", :nfkc)
true
```

Այս օրինակը ցույց է տալիս, թե ինչու չի կարելի NFKC կամ NFKD կիրառել միայն այն պատճառով, որ դրանք «ավելի ուժեղ» նորմալացում են թվում։ Եթե ծրագիրը պետք է պահպանի օգտագործողի գրած հայերեն տեքստը նույն ձևով, սովորաբար ավելի ապահով է ընտրել NFC։ Եթե որոնման կամ նույնականացուցիչների կանոնները պետք է `և` և `եւ` տարբերակները նույնը համարեն, այդ որոշումը պետք է բացահայտ սահմանել, փորձարկել և կիրառել բոլոր մուտքային տեքստային տվյալների նկատմամբ։

### Անվավեր UTF-8 տվյալների հայտնաբերումը

Elixir-ում string-ի և binary-ի համար կատարման ընթացքում առանձին տիպեր չկան։ Երկուսն էլ binary են։ Հետևաբար հնարավոր է ունենալ binary, որի բայթերը վավեր UTF-8 string չեն կազմում։

```elixir
iex> valid = "Բարև"
"Բարև"
iex> invalid = valid <> <<0xFF>>
<<212, 178, 213, 161, 214, 128, 214, 135, 255>>
```

`0xFF` բայթը չի կարող հայտնվել վավեր UTF-8 հաջորդականության մեջ։ `String.valid?/1` ֆունկցիան ստուգում է՝ binary-ն ամբողջությամբ վավեր UTF-8 է, թե ոչ։

```elixir
iex> String.valid?(valid)
true

iex> String.valid?(invalid)
false
```

Արտաքին աղբյուրից ստացված տվյալները պետք է ստուգել համակարգի սահմանին։ Այդպիսի աղբյուր կարող է լինել ֆայլը, socket-ը, սխալ կոդավորում օգտագործող հին API-ը կամ ձեռքով կազմված binary-ն։ Վեբ framework-ը կամ տվյալների ընթերցման գրադարանը երբեմն արդեն կատարում է այս ստուգումը, բայց դա պետք է հաստատել տվյալ գործիքի փաստաթղթով, ոչ թե ենթադրել։

### Անվավեր UTF-8 տվյալների փոխարինումը

Elixir 1.16-ից սկսած `String.replace_invalid/2` ֆունկցիան անվավեր բայթերը փոխարինում է տրված string-ով։ Եթե փոխարինող արժեք չի փոխանցվում, օգտագործվում է `�`՝ `U+FFFD REPLACEMENT CHARACTER` նշանը։

```elixir
iex> invalid = "Բարև" <> <<0xFF>>
iex> String.replace_invalid(invalid)
"Բարև�"

iex> String.replace_invalid(invalid, "?")
"Բարև?"
```

Փոխարինումը չի վերականգնում սկզբնական նշանը։ Այն միայն ստեղծում է վավեր UTF-8 string և ցույց է տալիս, որ տվյալ հատվածը հնարավոր չի եղել ճիշտ կարդալ։

Կարևոր տվյալների դեպքում, օրինակ՝ օգտատիրոջ նույնականացման համար անհրաժեշտ տվյալներ, վճարման նկարագրություն կամ ներմուծվող փաստաթուղթ, հաճախ ավելի ճիշտ է վերադարձնել սխալ և պահանջել վավեր մուտք։ Փոխարինումը հարմար է այն դեպքերում, երբ մասնակի տեքստը պահպանելն ավելի կարևոր է, օրինակ՝ վնասված log-ը ցուցադրելիս։ Ընտրությունը պետք է լինի գիտակցված և բացահայտ, ոչ թե պատահական։

### Տեքստի անվտանգ նախապատրաստումը

Համակարգ մուտք գործող տեքստը մշակելիս կարելի է հետևել պարզ հերթականության։

1. Ստուգել, որ արժեքը binary է։
2. Ստուգել UTF-8-ի վավերությունը։
3. Ընտրված ձևով նորմալացնել։
4. Կատարել ծրագրի պահանջած լրացուցիչ գործողությունները, օրինակ՝ հեռացնել եզրերի բացատները։

```elixir
def prepare_text(value) when is_binary(value) do
  if String.valid?(value) do
    normalized =
      value
      |> String.normalize(:nfc)
      |> String.trim()

    {:ok, normalized}
  else
    {:error, :invalid_utf8}
  end
end
```

Այս օրինակը ընտրում է խիստ մոտեցումը և անվավեր տվյալը չի փոխարինում։ Եթե տվյալների աղբյուրի համար թույլատրելի է կորցրած հատվածները `�` նշանով փոխարինել, `String.replace_invalid/1`-ը պետք է կիրառել մինչև նորմալացումը։

### Grapheme-ներով անվտանգ հասանելիությունը

UTF-8 string-ը չի կարելի անվտանգ կտրել պատահական բայթային դիրքում։ Հայերեն տառը երկու բայթ է զբաղեցնում, և միջից կտրված UTF-8 հաջորդականությունը դառնում է անվավեր։ Օգտատիրոջ տեսած նշաններով աշխատելու համար պետք է օգտագործել grapheme-ները հաշվի առնող ֆունկցիաներ։

`String.at/2`-ը վերադարձնում է նշված դիրքի grapheme-ը։ Դիրքերը սկսվում են `0`-ից։ Բացասական դիրքը հաշվվում է վերջից։ Եթե դիրքը string-ից դուրս է, վերադարձվում է `nil`։

```elixir
iex> String.at("Բարև", 0)
"Բ"

iex> String.at("Բարև", 3)
"և"

iex> String.at("Բարև", -1)
"և"

iex> String.at("Բարև", 10)
nil
```

`String.slice/3`-ը ընդունում է սկզբի դիրքը և անհրաժեշտ grapheme-ների քանակը։

```elixir
iex> String.slice("Բարև աշխարհ", 0, 4)
"Բարև"

iex> String.slice("Բարև աշխարհ", 5, 6)
"աշխարհ"
```

Այն ճիշտ է աշխատում նաև մի քանի code point-ից կազմված grapheme-ի հետ։

```elixir
iex> text = "e\u0301x"
"éx"

iex> String.slice(text, 0, 1)
"é"
```

`String.slice/3`-ի երրորդ արժեքը բայթերի քանակը չէ։ Այն grapheme-ների քանակն է։ Եթե պահանջը սահմանում է առավելագույն բայթերի քանակ, կարելի է օգտագործել `String.byte_slice/3`-ը։ Այն աշխատում է բայթային սահմանով, բայց չի վերադարձնում սկզբում կամ վերջում կիսատ մնացած code point։ Իսկ `binary_part/3` և `binary_slice/3` ցածր մակարդակի գործիքները կարող են UTF-8 code point-ը բաժանել բայթերի միջև, ուստի դրանք պետք է կիրառել միայն այն դեպքում, երբ իսկապես անհրաժեշտ է աշխատել անմշակ binary-ի հետ։

### String interpolation-ը

String interpolation-ը թույլ է տալիս արտահայտության արդյունքը տեղադրել string-ի մեջ։ Օգտագործվում է `#{}` գրելաձևը։

```elixir
iex> name = "Անի"
"Անի"

iex> "Բարև, #{name}"
"Բարև, Անի"

iex> "2 + 3 = #{2 + 3}"
"2 + 3 = 5"
```

Interpolation-ի մեջ կարելի է գրել Elixir արտահայտություն։ Դրա արդյունքը պետք է հնարավոր լինի վերածել string-ի `String.Chars` protocol-ի միջոցով։ Թվերը, atom-ները և բազմաթիվ այլ ստանդարտ տիպեր իրականացնում են այդ protocol-ը։

String-ում հատուկ նշանների համար օգտագործվում են escape sequence-եր։ Օրինակ՝ `\n`-ը նոր տող է, `\"`-ը՝ չակերտ, իսկ `\\`-ը՝ սովորական հակադարձ թեքագիծ։

```elixir
iex> "առաջին տող\nերկրորդ տող"
"առաջին տող\nերկրորդ տող"
```

IEx-ը արդյունքը ցուցադրում է escape sequence-ով, բայց տեքստը տպելիս `\n`-ը դառնում է իրական նոր տող։

### `~s` և `~S` sigil-ները

`~s` և `~S` sigil-ները նույնպես ստեղծում են string։ Դրանց առավելությունն այն է, որ կարելի է ընտրել հարմար սահմանազատիչ և նվազեցնել escape նշանների քանակը։

Փոքրատառ `~s`-ը կատարում է interpolation և մշակում է escape sequence-երը։

```elixir
iex> name = "Անի"
"Անի"

iex> ~s|Բարև, #{name}\n|
"Բարև, Անի\n"

iex> ~s|Նա ասաց՝ "Բարև"|
"Նա ասաց՝ \"Բարև\""
```

Մեծատառ `~S`-ը չի կատարում interpolation և չի մշակում escape sequence-երը։ Դրանք մնում են սովորական տեքստ։

```elixir
iex> name = "Անի"
"Անի"

iex> ~S|Բարև, #{name}\n|
"Բարև, \#{name}\\n"
```

`~S`-ը հարմար է այն տեքստերի համար, որոնց մեջ `#{}` կամ հակադարձ թեքագծերը պետք է պահպանվեն առանց փոփոխության։ Միակ պարտադիր escape-ը կարող է լինել ընտրված փակող սահմանազատիչը, եթե այն հանդիպում է հենց տեքստի մեջ։

### Մի քանի կիրառական `String` ֆունկցիա

`String` module-ը պարունակում է բազմաթիվ օգտակար ֆունկցիաներ։ Ստորև բերված են ամենօրյա աշխատանքում հաճախ օգտագործվող մի քանի ֆունկցիաներ։

#### Եզրերի բացատների հեռացում

`String.trim/1`-ը հեռացնում է string-ի սկզբի և վերջի Unicode whitespace նշանները։ Ներսի բացատները չեն փոխվում։

```elixir
iex> String.trim("  Բարև աշխարհ  ")
"Բարև աշխարհ"
```

Միայն սկզբից կամ վերջից հեռացնելու համար կան `String.trim_leading/1` և `String.trim_trailing/1` ֆունկցիաները։

#### Բաժանում

`String.split/3`-ը string-ը բաժանում է մասերի։ `trim: true` ընտրանքը հեռացնում է բաժանման հետևանքով առաջացած դատարկ տարրերը։

```elixir
iex> String.split("Elixir,Erlang,BEAM", ",")
["Elixir", "Erlang", "BEAM"]

iex> String.split("Elixir,,BEAM", ",", trim: true)
["Elixir", "BEAM"]
```

Եթե `String.split/1`-ին տրվում է միայն string-ը, այն բաժանում է Unicode whitespace-ի դիրքերում և անտեսում եզրերի բացատները։

```elixir
iex> String.split("  Բարև   աշխարհ  ")
["Բարև", "աշխարհ"]
```

#### Փոխարինում

`String.replace/4`-ը փոխարինում է կաղապարի բոլոր համընկնումները (4֊րդ պարամետրը ոչ պարտադիր է, օրինակում օգտագործվում է String.replace/3-ը)։

```elixir
iex> String.replace("Բարև աշխարհ", "աշխարհ", "Elixir")
"Բարև Elixir"
```

Փոխարինումը կարող է կատարվել նաև grapheme-ի ներսում գտնվող code point-ի նկատմամբ։ Եթե նորմալացման ձևը կարևոր է, string-ը պետք է նախ բերել ծրագրի ընդունած ձևին և միայն հետո որոնել կամ փոխարինել։

#### Սկիզբ, վերջ և պարունակություն

`String.starts_with?/2`, `String.ends_with?/2` և `String.contains?/2` ֆունկցիաները ստուգում են համապատասխան կաղապարի առկայությունը։

```elixir
iex> String.starts_with?("elixir-hy", "elixir")
true

iex> String.ends_with?("article.md", ".md")
true

iex> String.contains?("Բարև աշխարհ", "աշխարհ")
true
```

Այս ստուգումները ինքնաբերաբար նորմալացում չեն կատարում։ Արտաքինից նույն, բայց տարբեր code point-երով string-երը համեմատելուց առաջ պետք է կիրառել համապատասխան նորմալացման կանոնը։

#### Մեծատառ և փոքրատառ

`String.upcase/2`, `String.downcase/2` և `String.capitalize/2` ֆունկցիաների կիրառության օրինակներ․

```elixir
iex> String.upcase("Elixir")
"ELIXIR"

iex> String.downcase("ELIXIR")
"elixir"

iex> String.capitalize("elixir")
"Elixir"
```

#### Առաջին, վերջին և հակառակ հերթականություն

`String.first/1`, `String.last/1` և `String.reverse/1` ֆունկցիաներն աշխատում են grapheme-ներով։

```elixir
iex> String.first("Բարև")
"Բ"

iex> String.last("Բարև")
"և"

iex> String.reverse("e\u0301x")
"xé"
```

Վերջին օրինակում `e`-ն և combining acute accent-ը մնում են միասին։ Եթե string-ը շրջվեր առանձին code point-երով, շեշտը կարող էր առանձնանալ իր հիմնական տառից։

### Ո՞ր գործիքն ընտրել

Տեքստի մշակման ճիշտ եղանակը որոշվում է խնդրի բնույթով։ Տվյալների պահպանման կամ ցանցային արձանագրության չափը սովորաբար վերաբերում է բայթերին։ Unicode տվյալների ներքին վերլուծությունը կարող է պահանջել code point-եր։ Օգտատիրոջ տեսած տեքստի երկարությունը, դիրքը կամ հատվածը սովորաբար պետք է մշակել grapheme-ներով։

### Փորձեք ինքներդ

Բացեք IEx-ը և կատարեք հետևյալ քայլերը։

1. Համեմատեք `"\u00E9"` և `"\u0065\u0301"` string-երի `byte_size/1`, `String.codepoints/1`, `String.graphemes/1` և `String.length/1` արդյունքները։
2. Նույն երկու string-երը համեմատեք նախ `==`, ապա `String.equivalent?/2` գործիքով։ Բացատրեք արդյունքների տարբերությունը։
3. `"և"` string-ի նկատմամբ կիրառեք `:nfc`, `:nfd`, `:nfkc` և `:nfkd` ձևերը։ Յուրաքանչյուր արդյունքի համար հաշվեք code point-երն ու grapheme-ները։
4. Կազմեք անվավեր binary՝ վավեր string-ին ավելացնելով `<<0xFF>>`։ Ստուգեք այն `String.valid?/1`-ով, ապա փորձեք `String.replace_invalid/1` և `String.replace_invalid/2` տարբերակները։
5. Մի քանի code point-ից կազմված grapheme պարունակող string-ից առաջին նշանը ստացեք `String.slice/3`-ով։ Համոզվեք, որ combining mark-ը չի առանձնացել հիմնական տառից։
6. Նույն բովանդակությունը գրեք `~s` և `~S` sigil-ներով՝ ներառելով `#{}` և `\n`։ Համեմատեք արդյունքները։
